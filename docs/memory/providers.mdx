NeMo Relay defines a provider-neutral asynchronous contract and deterministic
reference provider. Provider-specific adapters live in application or
integration repositories so vendor SDKs do not enter Relay's Python, Node.js,
or Rust package closures.

## Adapter Contract

Only `search` and `store` are required. An adapter declares optional update,
delete, batch-store, maintenance, feedback, and health operations through
`MemoryCapabilities`. Callers check capabilities instead of inferring behavior
from a provider name.

Every operation uses explicit tenant and subject identity. Optional session and
agent fields can narrow a search but never broaden it. Returned records preserve
stable identity, content or an opaque reference, event and ingestion time,
provenance, neutral metadata, and provider-native metadata.

Provider adapters should run conformance cases for:

- Search and store behavior
- Record preservation and deterministic ordering
- Tenant and subject isolation
- Cross-session subject recall
- Idempotency and conflict handling
- Metadata and time filters
- Typed invalid requests and provider failures
- Every advertised optional capability

## Landing Boundary

Keep vendor SDKs, deployment configuration, service clients, live checks, and
provider-specific vocabulary outside NeMo Relay. An application can integrate
an adapter through public managed-call, middleware, plugin, subscriber, and
worker boundaries without changing Relay's neutral DTOs.

The five researched integration profiles are Mem0 OSS, Hindsight, Graphiti OSS,
Cognee, and Activeloop Hivemind. A separate companion project can preserve their
provider-native graph, temporal, reflection, consolidation, summary, and skill
semantics without presenting them as Relay package features.

<Warning>
Reserved adapter metadata is integrity-sensitive, not a cryptographic
signature. Use application-owned provider partitions and prevent untrusted
clients from writing the same reserved metadata.
</Warning>

## Current Limitation

The Python and Node reference automatic-memory components own native in-memory
providers. Arbitrary language-defined adapters cannot yet be passed directly
to those native components. External integrations can use Relay's public
lifecycle and middleware surfaces, or a separately deployed worker, while the
generic bridging API remains under design.
